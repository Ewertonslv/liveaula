## Concerns

### C-DA1: O core loop de 30s tem um risco de UX não auditável no plano

O product-spec.md define `< 30 segundos` como critério de lançamento inegociável. T12 (web) e T20 (mobile) implementam o formulário, mas **nenhum critério de acceptance mede o tempo real**. Um dev pode implementar o formulário corretamente em termos de campos e ainda assim atingir 90 segundos de preenchimento por conta de latência de carregamento da lista de alunos, ausência de smart defaults funcionando corretamente, ou UI de seleção lenta. O `acceptance criterion` de T20 é `npx tsc --noEmit` — não roda o app, não mede tempo. Recomendação: adicionar ao acceptance de T12 e T20 um teste cronometrado manual documentado (ex: video de preenchimento em <30s com dados reais do seed) antes de aprovar a task.

### C-DA2: `Subscription` está acoplada a 1 filho por pai — extensão futura é migration destrutiva

O model `Subscription { parentId: unique, studentId }` garante 1 subscription por pai e já a vincula a 1 filho. product-spec.md lista "múltiplos filhos" como `should-have`. Quando isso for implementado, a migration vai exigir: (1) remover `@unique` de `parentId`, (2) criar N subscriptions para o mesmo pai, (3) migrar pagamentos existentes. Isso é uma migration potencialmente destrutiva em dados financeiros reais. O schema deveria ter sido desenhado como `SubscriptionItem` desde o início. Não é crítico para o MVP mas é uma dívida técnica cara.

### C-DA3: Não há mecanismo de expiração automática de convites PENDING

Convites com `status = PENDING AND expiresAt < now()` nunca têm seu `status` atualizado para `EXPIRED` automaticamente — só são rejeitados no momento do acesso (`validateToken` checa `expiresAt > now()`). Isso significa que `GET /invitations?status=PENDING` do professor pode retornar convites tecnicamente expirados como PENDING. A UI na T13 mostra coluna "Expira em" mas o status ainda aparece PENDING. Solução simples: job de cleanup a cada hora no startup do servidor ou cálculo dinâmico no `GET /invitations` (filtrar `expiresAt > now()` para PENDING).

### C-DA4: Sem email transacional — cold-start depende de copiar link manualmente

Nenhuma das 25 tasks implementa envio de email. O produto-spec menciona "SendGrid ou Resend (transacional)" na stack. O fluxo de convite depende de o professor copiar a `inviteUrl` e enviar manualmente para o pai (via WhatsApp, provavelmente). Se o professor esquecer de enviar ou o link se perder, não há reenvio automático. Para MVP beta com primeiros usuários controlados isso pode ser aceitável — mas precisa ser decisão explícita documentada, não lacuna não percebida.

### C-DA5: Métricas de admin são calculadas em query sem cache — risco de timeout em produção

`GET /admin/metrics` calcula DAU, MAU, churnRate, conversionRate em uma única query agregada sobre Lessons e Subscriptions. Com dados reais de produção (1000+ lessons, 100+ subscriptions), sem índice especializado de analytics, essa query pode exceder 30s no PostgreSQL Railway free tier (512MB RAM, shared CPU). T8 não prevê cache nem materialized view. Adicionar pelo menos `revalidateTag` com TTL de 5min ou memoização simples com `Map<string, {value, expiresAt}>` em memória.

### C-DA6: Taxa de churn e conversão calculadas com fórmulas não especificadas

`GET /admin/metrics` retorna `churnRate: cancelledThisPeriod / totalAtStartOfPeriod` e `conversionRate: ACTIVE / (ACTIVE + CANCELLED + TRIAL expirado)`. Essas fórmulas dependem de `totalAtStartOfPeriod` — que requer snapshot do início do período. Sem isso, você precisa reconstruir o estado do banco no início de `from` (contagem histórica via `createdAt < from`). O plano não especifica como calcular `totalAtStartOfPeriod` sem audit log de mudanças de status. Se Subscription não tiver histórico de status transitions (só o status atual), `churnRate` é impossível de calcular corretamente com a fórmula proposta. Usar `Payment` como proxy (`cancelledThisPeriod = count subscriptions com cancelledAt BETWEEN from AND to`) é mais viável com o schema atual.
